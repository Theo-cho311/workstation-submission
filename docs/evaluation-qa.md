# 평가 질문과 답변 준비

아래 답변은 이 프로젝트 설계에 맞춘 연습용입니다. “성공했다”는 표현은 실제 로그를 확인한 뒤 사용하세요. 평가자가 반드시 이 질문만 한다는 뜻은 아닙니다.

## 1. 무엇을 만든 과제인가요?

“터미널에서 파일과 권한을 다루고, NGINX 기반 커스텀 이미지를 만들어 웹 페이지를 실행하는 개발 환경을 구성했습니다. 포트 매핑, 바인드 마운트의 변경 반영, 볼륨의 데이터 유지 여부를 확인하고 GitHub에 코드와 증거를 정리했습니다.”

증거 위치: README, Dockerfile, app/index.html, evidence의 단계별 로그.

## 2. 절대 경로와 상대 경로의 차이는?

절대 경로는 `/`에서 시작하는 전체 위치입니다. 예를 들어 `/home/noah/projects/workstation-submission/app`입니다. 상대 경로 `app`은 현재 디렉터리를 기준으로 합니다. `..`는 부모 디렉터리이고 `pwd`로 기준 위치를 확인합니다. 실습의 `$(pwd)/app`은 평가자 PC에서도 현재 프로젝트 위치를 기준으로 절대 경로를 만들기 위한 것입니다.

## 3. r, w, x와 755, 644는?

r은 4, w는 2, x는 1입니다. 세 자리 숫자는 소유자·그룹·기타 사용자 순서입니다. 755는 소유자 rwx, 그룹 r-x, 기타 r-x입니다. 644는 소유자 rw-, 그룹 r--, 기타 r--입니다.

파일의 r/w/x는 읽기/쓰기/실행입니다. 디렉터리의 r은 항목 이름 조회, x는 경로 통과와 항목 접근, w는 항목 추가·삭제 관련 권한이며 실제 조작에는 보통 x도 필요합니다. 파일 삭제 가능 여부는 파일 자체의 w만으로 결정되지 않고 부모 디렉터리 권한 등에 좌우됩니다.

## 4. 이미지와 컨테이너는 무엇이 다른가요?

이미지는 실행에 필요한 파일과 설정을 담은 템플릿이고 컨테이너는 그 이미지로 만든 실행 인스턴스입니다. 동일 이미지에서 여러 컨테이너를 만들 수 있습니다. 컨테이너에는 각자의 쓰기 가능한 계층이 있으며 컨테이너를 삭제하면 해당 계층도 사라집니다.

## 5. Docker는 가상머신과 같은가요?

컨테이너는 프로세스와 파일시스템 등을 격리하면서 기반 Linux 커널을 공유합니다. 각 컨테이너에 별도 전체 게스트 OS를 설치하는 일반적인 가상머신 방식과 차이가 있습니다. macOS/Windows의 Linux 컨테이너 환경에서는 Linux VM이 중간에 사용될 수 있습니다.

## 6. Dockerfile 각 줄은 무슨 뜻인가요?

`FROM nginx:stable-alpine`은 NGINX와 Alpine 기반의 기존 이미지를 선택합니다. `COPY app/ /usr/share/nginx/html/`은 기본 페이지를 내 콘텐츠로 교체합니다. `EXPOSE 80`은 컨테이너가 사용하는 포트를 문서화하며 실제 호스트 포트를 열지는 않습니다. NGINX 실행 명령은 베이스 이미지의 기본 설정을 그대로 사용합니다.

## 7. 어떤 커스텀 작업을 했나요?

“요구사항 A 방식으로 NGINX 웹 서버 베이스를 선택했습니다. 기본 환영 페이지를 한글 실습 페이지로 바꾸고 VERSION_1 표식을 넣어 바인드 마운트 변경 전후를 구별했습니다. 외부 라이브러리 없이 정적 HTML을 사용했습니다.”

## 8. build와 run의 차이는?

`docker build -t workstation-web:1.0 .`은 현재 폴더를 빌드 컨텍스트로 사용해 이미지를 만듭니다. `docker run`은 해당 이미지로 새 컨테이너를 생성·실행합니다. 이미 존재하는 컨테이너를 다시 켤 때는 `docker start`를 사용합니다.

## 9. 포트 매핑은 왜 필요한가요?

컨테이너의 네트워크 공간이 분리되어 있기 때문에 호스트에서 접근할 통로를 지정합니다. `-p 127.0.0.1:8080:80`은 내 PC의 8080 포트로 들어온 연결을 컨테이너 80 포트로 전달합니다. 127.0.0.1에 바인딩했으므로 다른 PC에 공개하는 설정은 아닙니다. 브라우저는 `http://localhost:8080`으로 접속합니다.

## 10. 바인드 마운트는 무엇을 확인했나요?

호스트의 app 폴더를 컨테이너의 웹 문서 폴더에 연결했습니다. 호스트에서 VERSION_1을 VERSION_2로 바꾼 뒤 같은 컨테이너로 요청하여 응답 변경을 확인합니다. 다시 build하지 않아도 반영됩니다. `readonly`는 컨테이너의 호스트 파일 수정만 막으므로 호스트에서 파일을 바꾸는 것은 가능합니다.

## 11. 볼륨과 바인드 마운트의 차이는?

바인드 마운트는 지정한 호스트 경로를 직접 연결하며 소스 편집에 편리합니다. 볼륨은 Docker가 관리하는 저장 공간이며 컨테이너와 별도 수명으로 데이터를 유지하는 데 적합합니다. 이 실습은 ws-data를 /data에 연결했습니다.

## 12. 데이터가 유지된다는 것을 어떻게 증명했나요?

“첫 번째 컨테이너에서 /data/proof.txt를 만들고 내용을 확인한 뒤 컨테이너를 stop과 rm으로 삭제했습니다. 다른 이름의 새 컨테이너에 같은 ws-data 볼륨을 연결해 동일한 내용을 읽었습니다. 서로 다른 컨테이너 ID와 같은 볼륨 이름도 확인했습니다.” 실제 결과는 evidence/volume.md에서 보여줍니다.

단순 stop/start는 컨테이너 삭제 후 영속성의 충분한 증거가 아닙니다. 볼륨 자체를 삭제하면 해당 데이터도 사라질 수 있습니다.

## 13. exec와 attach의 차이는?

exec는 실행 중인 컨테이너 안에 새 명령 프로세스를 실행합니다. attach는 기존 주 프로세스의 표준 입출력에 연결합니다. 이 실습은 주 프로세스가 Bash인 경우 exit하면 컨테이너가 종료되고, 주 프로세스가 sleep인 컨테이너에서 exec로 연 Bash만 exit하면 컨테이너는 유지되는 차이를 확인합니다. attach에서 Ctrl+P, Ctrl+Q로 분리하면 주 프로세스를 종료하지 않습니다.

## 14. -d, -it, --name은?

-d는 백그라운드 실행, -i는 표준 입력 유지, -t는 가상 터미널 할당입니다. -it는 대화형 셸에서 함께 사용합니다. --name은 컨테이너 이름이며 종료되어 있어도 기존 컨테이너 이름을 다시 쓸 수 없습니다.

## 15. 운영 명령을 설명해 보세요.

| 명령 | 확인하는 것 |
|---|---|
| docker images | 로컬 이미지 목록 |
| docker ps / ps -a | 실행 중 / 종료 포함 컨테이너 |
| docker logs 이름 | 컨테이너 표준 출력·오류 로그 |
| docker stats --no-stream 이름 | 자원 사용량 한 번 조회 |
| docker info | 엔진 연결 및 서버 정보 |
| docker stop 이름 | 정상 종료 신호를 통한 중지 요청 |
| docker rm 이름 | 컨테이너 삭제 |

## 16. Git과 GitHub의 차이는?

Git은 내 PC에서 변경 이력을 관리하는 도구이고 GitHub는 Git 저장소를 원격에 호스팅해 공유·협업하도록 돕는 서비스입니다. Git 사용자 이름을 설정했다고 GitHub에 로그인된 것은 아닙니다.

## 17. add, commit, push는?

add는 다음 커밋에 포함할 변경을 스테이징하고, commit은 로컬 이력을 남기고, push는 로컬 커밋을 원격 저장소에 보냅니다. main은 기본 브랜치 이름이며 origin은 보통 사용하는 원격 저장소 별칭입니다.

## 18. 겪은 문제 두 가지를 설명해 보세요.

“권한 000인 실습 파일을 읽으려 하자 실패했습니다. ls -l로 확인하고 644로 바꿔 다시 읽었습니다. 또 종료된 컨테이너와 동일한 이름으로 새 컨테이너를 만들면 오류가 났습니다. ps -a로 남아 있는 컨테이너를 확인하고 실습 컨테이너를 삭제해 해결했습니다. 두 사례는 원리 확인을 위해 의도적으로 재현했습니다.” 실제 오류 문구를 확인한 후 답합니다.

## 19. 다른 PC에서도 재현할 수 있나요?

Docker가 준비된 환경에서 저장소를 복제하고 README 절차대로 build/run하면 같은 소스와 설정으로 실행할 수 있습니다. 호스트 app 경로는 $(pwd)로 계산합니다. 8080이 사용 중이면 다른 호스트 포트를 사용하고 기록해야 합니다. CPU 아키텍처와 Docker 지원 환경도 영향을 줍니다.

`stable-alpine`은 시간이 지나면 다른 이미지로 바뀔 수 있는 태그입니다. 실습 로그에 실제 RepoDigest를 남깁니다. 정확히 같은 베이스 바이트를 고정하려면 확인한 digest로 FROM을 고정하고 다시 빌드·검증해야 합니다. “어느 시점에나 완전히 동일”하다고 과장하지 않습니다.

## 20. 비밀정보는 어떻게 보호했나요?

로그와 스크린샷에서 인증정보를 제외하고 .env, 개인키 패턴을 .gitignore에 넣었습니다. .gitignore는 이미 추적 중인 파일이나 로그 속 비밀정보를 자동 제거하지 않습니다. 커밋 전에 실제 변경 내용을 검사해야 합니다.

## 평가 직전 5분 확인

1. Dockerfile의 FROM/COPY/EXPOSE를 설명한다.
2. 8080 → 80과 접속 주소를 설명한다.
3. 바인드 마운트와 볼륨의 차이를 말한다.
4. 삭제 전후 볼륨 로그와 권한 변경 전후 로그를 직접 찾는다.
5. GitHub의 README에서 모든 증거가 열리는지 확인한다.
